## What does the computer see?

An **expression** is anything that produces a value: `42`, `price`, `price * quantity + 5`, `len(name) > 3`. A **statement** is an instruction that *does* something: `total = price * 2`, `print(total)`. Statements usually contain expressions.

Here's the question. When you write

```python
2 + 3 * 4
```

how does Python know to compute `3 * 4` first? You see a line of characters. The computer, after parsing, sees a **tree**:

To evaluate a tree, start at the leaves and work up. Each operator node combines the values of its children. The root's value is the value of the whole expression.

> **The big picture.** Text is a flat line, but meaning is a tree. Precedence rules, associativity and parentheses are all just ways of deciding **which tree** a line of text stands for. Once the tree is built, evaluation is mechanical.

This tree is called an **abstract syntax tree** (AST), and it's the central data structure of every compiler and interpreter. You can even ask Python for it: `import ast; print(ast.dump(ast.parse("2 + 3 * 4", mode="eval")))`. And look at the order you visit the nodes when you evaluate bottom-up, left to right: `2 3 4 * +`. That's **Reverse Polish Notation**, Tuesday's exercise. A stack machine evaluates the tree by visiting it in exactly that order.

## Precedence and associativity

**Precedence** decides which operator binds tighter, i.e. ends up lower in the tree. Python's arithmetic follows school maths, from tightest to loosest:

| Precedence | Operators |
| --- | --- |
| highest | `**` (power) |
| | unary `-x`, `+x` |
| | `*`, `/`, `//`, `%` |
| | `+`, `-` |
| | comparisons `<`, `<=`, `==`, `!=`, … |
| | `not` |
| | `and` |
| lowest | `or` |

**Associativity** decides the tree when operators have the *same* precedence. Most are **left-associative**: `10 - 4 - 3` means `(10 - 4) - 3 = 3`, not `10 - (4 - 3) = 9`. The exception is `**`, which is **right-associative**, like in maths: `2 ** 3 ** 2` is $2^{(3^2)} = 2^9 = 512$, not $(2^3)^2 = 64$.

One trap: `-2 ** 2` is `-4`, because `**` binds tighter than the unary minus. The tree is `-(2 ** 2)`.

**The professional rule:** when in doubt, add parentheses. Code is read far more often than it's written, and `(a * b) + c` costs you nothing.

## Integer division and remainder

Two operators you'll use constantly, often together:

- `a // b` is **floor division**: divide, then round **down** to the nearest integer.
- `a % b` is the **remainder** (modulo).

They're linked by one equation, which Python guarantees for all integers (with $b \ne 0$):

$$
a = b \cdot (a \mathbin{//} b) + (a \mathbin{\%} b).
$$

For positive numbers this is primary-school division: `17 // 5` is `3`, `17 % 5` is `2`, and $17 = 5 \cdot 3 + 2$. The surprise comes with negatives. "Round down" means toward $-\infty$, so `-17 // 5` is `-4`, not `-3`. Then the equation forces `-17 % 5` to be `3`: $-17 = 5 \cdot (-4) + 3$.

In Python the remainder always has the **same sign as the divisor**. That makes `%` perfect for "wrapping around". `(hour + 5) % 24` is always a valid hour, even when going backwards: `(2 - 5) % 24` is `21`. (Careful: C and Java round toward zero instead, so there `-17 % 5` is `-2`. Same symbol, different rule: always check.) This is the "same remainder" equivalence relation from Thursday's issue of The Daily Theorem, running on a computer.

## Lazy logic: short-circuit evaluation

`and` and `or` are evaluated **lazily**, left to right, stopping as soon as the answer is known:

- In `A and B`, if `A` is false, the result is false whatever `B` is, so **`B` isn't evaluated at all**.
- In `A or B`, if `A` is true, `B` isn't evaluated.

This isn't just an optimisation. It's used to write safe code:

```python
count = 0
total = 10
if count != 0 and total / count > 2:
    print("big average")
```

If `count` is 0, the division never happens, so there's no `ZeroDivisionError`. Swap the two conditions and the program crashes. In a tree picture, `and` is a node that may decide **not to visit its right child**.

One more Python peculiarity: `and` and `or` return one of their *operands*, not necessarily `True` or `False`. `0 or 5` is `5`, `"" or "default"` is `"default"`. That gives the common idiom `name = user_input or "anonymous"`.

And comparisons chain like in maths: `0 <= x < 10` means `0 <= x and x < 10`.

> **Why it matters.** Precedence bugs, negative-modulo bugs and evaluation-order bugs are classic, and they hide in plain sight because the code *looks* right. Thinking in trees is also the foundation of compilers (weeks 54–56), of how calculators and spreadsheets work, and of how databases plan queries (week 43).
