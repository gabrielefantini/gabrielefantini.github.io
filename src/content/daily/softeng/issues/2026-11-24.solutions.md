**1.** (a) **Compiled.** A tiny processor has little memory and speed to spare, and there's no room for an interpreter. You want lean, fast machine code, checked before it ships. This is why embedded software is mostly C (week 97).
(b) **Interpreted** (or an interactive REPL). The feedback loop "type, see, adjust" matters more than raw speed. This is why data science lives in Python notebooks.
(c) **Compiled to a single executable.** Users shouldn't have to install an interpreter and the right versions of its libraries. Go and Rust are popular for command-line tools for exactly this reason.
(d) **Interpreted.** It runs once and takes milliseconds either way, so compiling would just slow *you* down.

**2.** First run: **nothing is printed at all**. Python reports

```text
  File "a.py", line 3
    x = 1 +
           ^
SyntaxError: invalid syntax
```

Python *compiles the whole file to bytecode before running any of it*, and a syntax error makes that compilation fail. So even line 1 never runs.

After fixing line 3 (say `x = 1 + 1`), the output is

```text
start
middle
Traceback (most recent call last):
  File "a.py", line 4, in <module>
    print(undefined_name)
NameError: name 'undefined_name' is not defined
```

The file now compiles fine. A misspelled name is grammatically valid. The mistake is only discovered **when line 4 actually runs**, after the first two lines have already done their work. That's the hybrid nature of CPython in action: grammar is checked up front (compiler), names are looked up at run time (interpreter). A compiled, statically typed language like Java or C would reject the undefined name before running anything. Linters for Python (week 9) close part of this gap.

**3.** **Machine code** is the instruction set of a *real* processor family: x86-64 instructions mean nothing to an ARM chip, and vice versa. **Bytecode** is the instruction set of a *virtual* machine that exists only as software. A `.class` file contains JVM bytecode, and each platform has its own JVM (itself compiled to that platform's machine code) that knows how to run it. So the bytecode is portable, and the virtual machine is the part that's ported. A compiled C program contains, say, x86-64 machine code that an ARM CPU can't decode. You'd have to recompile it for ARM.

**4.** For example:

```python
import dis

def sign(x):
    if x > 0:
        return "positive"
    return "not positive"

dis.dis(sign)
```

prints, among other lines, `POP_JUMP_IF_FALSE` (the exact name varies by Python version). It means: "take the result of the comparison off the stack; if it's false, jump over the `return "positive"` block". It's Monday's `JNZ`: a **conditional jump**. Every `if`, `while` and `for` becomes conditional jumps like this one.

**5. ★**

```python
def rpn(expression):
    """Evaluate an expression in Reverse Polish Notation."""
    stack = []
    for token in expression.split():
        if token in ("+", "-", "*", "/"):
            if len(stack) < 2:
                raise ValueError(f"'{token}' needs two operands")
            b = stack.pop()          # the top of the stack is the RIGHT operand
            a = stack.pop()
            if token == "+":
                stack.append(a + b)
            elif token == "-":
                stack.append(a - b)
            elif token == "*":
                stack.append(a * b)
            else:
                stack.append(a / b)
        else:
            stack.append(float(token))
    if len(stack) != 1:
        raise ValueError(f"expected one result, found {len(stack)} values")
    return stack[0]


print(rpn("3 4 +"))              # 7.0
print(rpn("5 1 2 + 4 * + 3 -"))  # 14.0
```

`rpn("5 1 2 + 4 * + 3 -")` returns **14.0** (a float, because we parse numbers with `float` so that `/` works).

Two details matter. First, **the order of the pops**: the value on top of the stack is the *second* operand, so `10 2 -` is $10 - 2 = 8$, not $-8$. Second, **errors**: `"1 +"` reaches `+` with only one value on the stack, so we raise a clear `ValueError` instead of crashing with an obscure `IndexError` from `pop()`. `"1 2"` ends with two values and no operator, which is also an error. Callers can catch these with `try`/`except` (week 8).

You've just written an **interpreter**: it reads a program (the token string) and carries it out step by step, using a stack. It's the same design as Python's bytecode machine. RPN is also exactly the order in which a compiler emits code for an expression tree, as you'll see on Thursday.
