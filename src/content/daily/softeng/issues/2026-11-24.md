## Two kinds of translator

Suppose you need an Italian novel in English. You hire a **translator**. She takes the whole book home, works on it for months, and hands you an English book. From then on you can read it as often as you like, as fast as you like, without her.

Now suppose an Italian diplomat is giving a speech, live. You hire an **interpreter**. He stands next to you and translates each sentence as it's spoken. Nothing is written down. If you want to hear the speech again, he has to interpret it again.

Programming languages work exactly the same way:

- A **compiler** translates the whole source program into machine code *ahead of time*, producing an executable file. Then the executable runs on its own, without the compiler. C, C++, Rust and Go work like this.
- An **interpreter** reads the source program and *carries it out* directly, statement by statement, every time it runs. Classic shells (`bash`) and early BASIC work like this.

## The trade-offs

Neither approach is "better". They optimise for different things.

| | Compiled | Interpreted |
| --- | --- | --- |
| **Speed of the running program** | fast: no translation at run time | slower: translation work at every step |
| **Time from edit to run** | must recompile first | instant |
| **When are errors found?** | many at compile time, before running | often only when the faulty line runs |
| **Distribution** | ship an executable (one per platform) | ship source; needs the interpreter installed |
| **Interactivity** | hard | natural: type a line, see the result |

The third row matters a lot for software engineering. A compiler reads your *whole* program before running any of it, so it can catch a whole class of mistakes (typos in names, type mismatches in typed languages) **before a user ever sees them**. An interpreter may happily run for an hour and then crash on a typo in a line it had never reached before.

## The truth: almost everyone is a hybrid

Real-world languages mostly combine both ideas:

**Bytecode + virtual machine.** Python and Java *compile* your source code, but not to the CPU's machine code. They compile to **bytecode**, the machine code of an imaginary, simplified computer. Then a program called a **virtual machine** *interprets* that bytecode. It's exactly Monday's toy CPU, written in C instead of Python.

You can see Python's bytecode yourself:

```python
import dis

def total(price, quantity):
    return price * quantity + 5

dis.dis(total)
```

The output (it varies a little between Python versions) looks like this:

```text
LOAD_FAST     price
LOAD_FAST     quantity
BINARY_OP     *
LOAD_CONST    5
BINARY_OP     +
RETURN_VALUE
```

Look familiar? It's Monday's `LOAD` / `MUL` / `ADD` machine, slightly more grown-up. Python keeps a *stack* of values instead of one accumulator (we'll meet stacks in week 16), but the idea is identical.

Why the detour through bytecode? Bytecode is **portable**: the same `.class` file runs on any computer that has a Java virtual machine. Your Python code runs anywhere Python is installed. And checking the program once while turning it into bytecode is cheaper than re-reading raw text at every step.

**Just-in-time (JIT) compilation.** The cleverest virtual machines (Java's HotSpot, JavaScript's V8 in your browser, PyPy) watch the program as it runs. When a piece of code runs often ("it's hot"), they compile *that piece* to real machine code, on the fly. You get the instant start of an interpreter and, for the code that matters, the speed of a compiler.

> **The big picture.** "Compiled vs interpreted" isn't a property of a *language*. It's a property of an *implementation*. Python is usually run by an interpreter (CPython), but PyPy JIT-compiles it. C is usually compiled, but C interpreters exist. The real question is always: *when* does translation happen, and how much of it?

You'll build your own compiler, piece by piece, in weeks 54–56. Today's exercise 5 is your first step.

> **Why it matters.** Knowing what your language's implementation does explains things that otherwise look like magic: why Python loops are slow and NumPy is fast (NumPy calls compiled C code), why Java programs "warm up", why a typo can hide in Python code for months, and why Go can ship a single binary file that just runs.

**5. ★** Write an **interpreter** for arithmetic in *Reverse Polish Notation* (RPN), where operators come after their operands: `3 4 +` means $3 + 4$, and `5 1 2 + 4 * + 3 -` means $5 + (1 + 2) \cdot 4 - 3 = 14$. Use a Python list as a stack: read tokens left to right; push numbers; for an operator, pop two values, apply it, and push the result. Your function `rpn("5 1 2 + 4 * + 3 -")` should return `14`. What should happen with `"1 +"`? Make your interpreter report an error instead of crashing.
