## A recipe for a very literal cook

Imagine a cook who follows recipes **perfectly literally**. "Add salt" — how much? They freeze. "Bake until golden" — what's golden? They freeze. "Crack two eggs into the bowl" — they crack the eggs and drop them in, shells and all, because nobody said to remove the shells.

That cook is a computer. It has no common sense and no idea what you *meant*. It has a short list of tiny operations it can perform with total precision and astonishing speed (a few billion per second), and nothing else.

A **program** is a recipe written for that cook. Every step must be:

- **unambiguous**: exactly one way to read it;
- **executable**: one of the operations the machine actually knows;
- **finite**: the recipe has to say when to stop.

Software engineering, the subject of this newspaper for the next two years, is the craft of writing those recipes so they're *correct*, *understandable by other humans*, and *cheap to change*. Today we start at the very bottom: what physically happens when a program runs?

## From text to electrons

You write programs in a **programming language** such as Python, C or Java, as plain text. That text is called **source code**:

```python
price = 20
quantity = 3
total = price * quantity
print(total)
```

But the processor (CPU) can't read Python. It understands only **machine code**: sequences of numbers, each encoding one tiny instruction like "add the contents of two registers" or "jump to instruction 17". Something has to bridge the gap:

The translator is itself a program, either a **compiler** or an **interpreter**. We'll spend tomorrow on the difference. Today, let's look at the right-hand box: what the CPU does with machine code.

## The heartbeat: fetch, decode, execute

A CPU is surprisingly simple at heart. It has:

- a **memory**, a long row of numbered cells, each holding a number;
- a few super-fast cells inside the CPU called **registers**;
- a special register called the **program counter** (PC), which holds the address of the next instruction.

And it repeats one loop, forever, billions of times a second:

1. **Fetch:** read the instruction at address PC.
2. **Decode:** work out what it means ("add", "load", "jump"…).
3. **Execute:** do it, and move PC to the next instruction (or somewhere else, if it was a jump).

> **The big picture.** Everything a computer has ever done — showing this page, running a game, training an AI — is this three-step loop, repeated. The magic isn't in any single step. It's in the number of steps per second and in how cleverly we arrange them.

The best way to understand a loop is to build one. Here's a complete toy computer in Python. Don't worry if some syntax is new (we'll cover all of it in the coming weeks). Read it as a recipe.

```python
# A toy CPU with one register (the "accumulator") and four instructions.
program = [
    ("LOAD", 20),    # acc = 20
    ("MUL", 3),      # acc = acc * 3
    ("ADD", 5),      # acc = acc + 5
    ("PRINT", None), # show acc
    ("HALT", None),  # stop
]

acc = 0   # the accumulator register
pc = 0    # the program counter

while True:
    op, arg = program[pc]        # FETCH the instruction at pc
    pc = pc + 1                  # point at the next one
    if op == "LOAD":             # DECODE and EXECUTE
        acc = arg
    elif op == "ADD":
        acc = acc + arg
    elif op == "MUL":
        acc = acc * arg
    elif op == "PRINT":
        print(acc)
    elif op == "HALT":
        break
```

Run it (save it as `toy.py`, then `python3 toy.py`) and it prints `65`. Our machine has a **program** (a list of instructions), a **register** (`acc`), a **program counter** (`pc`), and the **fetch–decode–execute loop** (`while True`). A real CPU is this, with a few hundred instructions instead of five, implemented in silicon rather than Python.

Notice the deepest idea in that code: **the program is data.** It's a list sitting in memory, just like the numbers it computes with. This is the *stored-program* idea of John von Neumann (1945), and it's why the same machine can run a spreadsheet one second and a game the next. You'll study it properly in week 13.

## So why not write machine code directly?

You could, and the first programmers did, with switches and punched cards. But even our toy machine needs a separate instruction for every tiny step, and real machine code is far more detailed: which register, which memory address, how many bytes. Programming languages exist so you can think in **your** terms (prices, quantities, totals) rather than the machine's terms (registers, addresses). Every layer of abstraction, from machine code to assembly to C to Python, trades a little control for a lot of clarity.

> **Why it matters.** "What is the machine actually doing?" is the question behind every performance problem, every security hole and every mysterious bug. You won't think about registers every day, but knowing they're down there is what separates programmers who guess from engineers who understand.
